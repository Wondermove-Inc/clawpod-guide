# Provider와 model 선택

Agent는 하나의 model만 쓰도록 고정할 필요가 없습니다. Portal의 Agent 생성·설정 흐름은 **main**, **sub**, **fallback**, **heartbeat** 역할별 model을 선택할 수 있습니다. 이 선택은 Agent가 실제로 호출할 provider credential, model catalog, runtime release와 함께 맞아야 합니다.

## Cloud에서 관리하는 provider

| provider | Credential 형태 | Portal에서의 model 선택 방식 |
| --- | --- | --- |
| Anthropic | API key 또는 setup token | 일반 selector의 provider. Agent binding은 API key만 허용됩니다. |
| OpenAI | API key | 일반 selector의 provider |
| OpenAI Codex | ChatGPT 로그인 또는 `auth.json` | 일반 selector의 provider. subscription 기반 candidate는 catalog 상태에 따라 표시됩니다. |
| Google Gemini | API key | 일반 selector의 provider |
| OpenRouter | API key | 일반 selector에서 catalog의 model을 통합해 표시할 수 있습니다. |
| Local LLM (Ollama) | server URL, 선택 model | local server 연결·test 뒤 선택 model을 역할에 자동 배정할 수 있습니다. API key는 지원하지 않습니다. |
| OpenAI-compatible | server URL, 선택 model, 필요 시 API key | local server 연결·test 뒤 선택 model을 역할에 자동 배정할 수 있습니다. |

Portal의 credential dialog는 Anthropic, OpenAI, OpenAI Codex, Google, OpenRouter, Local LLM의 여섯 service 선택지를 제공합니다. Local LLM 안에서 Ollama와 OpenAI-compatible server를 구분하므로, runtime provider identifier는 표처럼 일곱 가지가 됩니다. Portal의 hosted provider selector는 앞의 다섯 hosted provider를 기준으로 동작합니다.

API key 발급은 [Credential 관리](./manage-credentials.mdx#provider-api-key-발급하기)를, OpenAI Codex 연결은 [ChatGPT 로그인 안내](./manage-credentials.mdx#openai-codex-로그인으로-연결하기)를 따르세요. Portal에서 로그인하거나 기존 `auth.json`을 직접 등록할 수 있습니다.

연결 방법은 Portal에서 제공하는 설정과 각 서비스의 사용 조건을 따릅니다.

## model 목록은 왜 고정 표가 아닌가요?

선택 가능한 모델은 Portal의 목록에서 확인하세요. 서비스와 모델의 활성 상태가 달라질 수 있어 이 문서에는 고정된 전체 모델 목록을 두지 않습니다.

모델을 선택할 때 해당 AI 연결과 사용 조건을 확인합니다. 원하는 모델이 보이지 않으면 이름을 지침 파일에 넣어 적용하려 하지 말고 조직 관리자에게 문의하세요.

## 역할별 선택 원칙

| 역할 | 용도 | 선택 원칙 |
| --- | --- | --- |
| main | 최종 판단과 주요 응답 | 업무 품질·tool compatibility·비용을 함께 검토합니다. |
| sub | 조사, 초안, 보조 작업 | main보다 가벼운 model을 쓸 수 있지만 민감 판단을 위임하지 않습니다. |
| fallback | main 호출 실패 시 대체 | main과 다른 provider를 쓰면 그 provider credential도 연결해야 합니다. |
| heartbeat | 정기 점검 turn | 짧은 점검에 맞는 model을 선택하고, heartbeat 자체가 Cloud self-service scheduler라는 뜻은 아닙니다. |

fallback은 “항상 더 싼 model”이 아니라 **실제로 인증·호출 가능한 대체 경로**여야 합니다. main과 fallback이 서로 다른 provider라면, 두 credential을 모두 연결하고 test Room에서 각각 작동을 확인하세요.

## 설정 절차

새 Agent는 [Agent 생성](./create-agent.mdx) 화면에서 역할별 모델과 인증 정보를 선택합니다. 기존 Agent의 모델은 다음 순서로 변경합니다.

1. 필요한 provider Credential을 [AI Key와 Credential 관리](./manage-credentials.mdx)에서 준비합니다.
2. **에이전트** 목록에서 대상 Agent의 상세를 열고 **AI 리소스 설정 → 수정**을 선택합니다.
3. 메인·서브·폴백·하트비트의 제공자와 모델을 필요한 범위에서 변경합니다.
4. 저장된 키 선택 또는 키 직접 입력 영역에서 각 제공자에 필요한 인증 정보를 설정합니다. 선택한 Credential이 같은 tenant에서 사용 가능한지 확인합니다.
5. 진행 중인 작업에 미칠 영향을 확인한 뒤 **저장 후 재시작**을 선택합니다. 변경하지 않으려면 **취소**를 선택합니다.
6. Agent가 다시 실행 가능한 상태인지 확인하고 비민감 test Room에서 작은 요청으로 모델 응답과 필요한 도구 동작을 확인합니다.
7. 비용·오류·latency는 [Analytics](./use-analytics.mdx)에서 추적하고, 문제가 생기면 한 번에 여러 역할을 바꾸지 않습니다.

## Local LLM 사용 시 전제조건

Local LLM은 Ollama 또는 OpenAI-compatible server를 등록하고 연결 test를 통과해야 합니다. 선택 model의 parameter size 정보가 있으면 Portal은 큰 model을 main, 작은 model을 heartbeat처럼 역할에 자동 배정할 수 있습니다. 자동 배정 결과도 그대로 승인하지 말고, server 접근 범위·성능·privacy·fallback을 확인하세요.

연결 테스트 성공 뒤에도 대상 Agent에서 실제 모델 응답을 확인하세요. 서버 접근 권한과 선택한 모델의 준비 상태가 맞아야 합니다.

## 다른 연결이 필요한 경우

이 가이드에서 안내하는 연결은 위 표의 서비스입니다. 다른 연결이 필요하면 현재 Portal에 지원되는 설정 경로가 있는지 확인하세요. 설정 방법을 추측하거나 비밀값을 대화에 넣지 마세요.
