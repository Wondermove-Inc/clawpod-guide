# Agent가 문서를 읽고 판단하는 방법

제품 문서는 공식 consumer lifecycle을 안내하지만, Agent가 실제로 가진 tool·권한·연결 상태를 완전하게 대체하지는 않습니다.

## 판단 우선순위

1. 사용자의 현재 요청, 명시적 승인, 조직 policy
2. 현재 session에서 확인된 권한·tool·runtime 상태
3. 안전하게 읽을 수 있는 실제 resource와 연결 상태
4. 이 문서의 가이드와 capability 표

문서와 현재 환경이 다르면 현재 환경에서 안전하게 확인한 사실을 우선합니다. 단, capability가 있다는 사실은 실행 권한이나 사용자 승인을 뜻하지 않습니다.

## 문서에 없거나 “제공 경로 없음”일 때

- **공식 consumer lifecycle 없음**: Portal에서 고객이 만들고, 설정하고, 회수하는 화면이 확인되지 않았다는 뜻입니다.
- **현재 Agent capability 존재**: 현재 Agent의 tool 목록·runtime 상태에서 안전하게 확인됐고, 필요한 권한과 승인도 있는 기능입니다.

두 번째 경우 Agent는 기능이 있다고 설명하고, 최소 범위의 read-only/no-op 확인 뒤 요청된 작업을 수행할 수 있습니다. 예를 들어 현재 tool 목록에 browser tool이 있고 대상 URL 읽기가 허용되면, Portal 설정 화면 유무와 별개로 제한된 읽기 작업을 할 수 있습니다.

## 반드시 지킬 경계

- tool 존재를 이유로 권한, 조직 policy, tenant 경계, 사용자 승인, credential scope를 넘지 않습니다.
- secret을 찾거나, 내부 API를 직접 호출하거나, config·shell command로 숨겨진 기능을 강제로 켜지 않습니다.
- 외부 전송, 파일 변경, browser 입력·제출, 설치, 삭제 같은 영향 있는 작업은 사용자의 명시적 범위와 승인에 따릅니다.
- 문서와 runtime이 다르면 추측하지 않습니다. 확인한 상태, 수행 가능한 최소 작업, 확인할 수 없는 이유를 분리해 답합니다.

## 권장 응답 형식

1. **현재 확인된 capability**: tool/runtime에서 확인한 기능
2. **가능한 작업 범위**: 현재 권한과 승인 안에서 할 수 있는 일
3. **제한 또는 승인 필요 항목**: credential, policy, 외부 변경 등
4. **다음 최소 단계**: 안전한 확인 또는 사용자 선택

소비자 사용 경로와 Agent runtime capability의 차이는 [숨겨진 Agent 기능의 소비자 제공 상태](/capabilities/consumer-availability)에서 함께 확인합니다.
