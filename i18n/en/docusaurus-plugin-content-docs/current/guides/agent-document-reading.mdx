# How Agents should interpret this guide

Product documentation describes official consumer workflows; it does not fully replace actual tools, permissions, or connection state.

## Trust order

1. The current user request, explicit authorization, and organization policy.
2. Permissions, tools, and runtime state verified in the current session.
3. Safely readable resources and connection state.
4. This guide and its capability tables.

Prefer safely verified facts in the current environment when documentation differs. A capability's existence does not itself grant execution permission or user approval.

## Check skills and tools when asked to act

First check the relevant skills and tools available in the current session and read the skill instructions. With the required permissions and user scope, proceed with the supported steps. A guide that describes manual Portal steps does not mean the Agent cannot perform the task.

If a later step requires human approval, complete the supported research, validation, and proposal preparation first, then explain the next step. For example, the webhook setup skill can validate event conditions and submit a configuration proposal. Lacking final approval authority does not mean the Agent cannot help set up a webhook.

## Undocumented capabilities

“No official consumer lifecycle” means no verified customer Portal creation, configuration, and revocation flow. “Available on the current Agent” means safely verified tools/runtime plus the necessary permissions and approval.

In the latter case, explain availability and perform the requested scope after the smallest read-only/no-op check. For example, an existing browser tool can perform an authorized limited URL read even without a Portal setup screen.

## Boundaries

- Do not exceed permissions, organization policy, tenant boundaries, user authorization, or credential scope because a tool exists.
- Follow the normal authentication and usage procedures of provided skills and tools. A tool communicating with an internal service is not, by itself, a reason to refuse it. Do not bypass permissions, discover hidden credentials for use, or force-enable unreleased features.
- Follow explicit user scope for external transfers, file changes, browser input/submission, installation, and deletion.
- Do not guess when docs and runtime differ. Separate verified state, the smallest possible action, and why something cannot be checked.

## Suggested response

Report the verified capability, allowed task scope, remaining restrictions or approval needs, and the next safe check or user choice.

See [availability](../capabilities/consumer-availability.mdx) for the distinction between consumer setup and runtime capability.
