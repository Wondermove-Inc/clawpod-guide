# Send webhook events to an Agent

This workflow sends external events to a chosen Agent or Chat Room. Sources with a signing secret and verifier validate signatures.

## Ask an Agent to set up a webhook

You can ask an Agent to prepare a webhook integration. First have it check that the `webhook-integration-setup` skill and related tools are available, then follow the skill instructions.

> Set up a webhook to receive events from this service. Check the `webhook-integration-setup` skill and use it to proceed. Ask me for any information you need.

1. The Agent clarifies the service and events you want and asks for missing details.
2. It checks provider information and official documentation, validates conditions against sample events, and submits a configuration proposal.
3. A user with webhook management permissions reviews and approves the proposal in the Portal. Approval creates the integration.
4. The user registers the receiving URL and required secret in the external service's console.
5. Send a test event and check event records and the target's response. You can ask the Agent to check proposal status and whether the first event has arrived.

The skill supports research, condition validation, proposal submission, and status checks. The user handles final approval and external service registration. While approval is pending, the Agent explains the remaining steps rather than submitting a duplicate proposal.

You can also start from **Webhooks → New integration → Set it up with an agent** and choose a Room. The following sections describe manual Portal setup.

Before starting, obtain Source and Rule creation permission, choose the receiving organization and Agent/Room, and confirm the external service supports an HTTPS webhook URL and signing secret. Minimize recipients and Playbook content because payloads may contain customer data.

## Create a Playbook

1. Open <strong><span data-ui-label="nav.webhooks">Webhooks</span></strong> → <strong><span data-ui-label="webhooks.playbooks.title">Playbooks</span></strong> → <strong><span data-ui-label="webhooks.playbooks.create">Create Playbook</span></strong>.
2. Enter <strong><span data-ui-label="webhooks.playbooks.name">Name</span></strong> and <strong><span data-ui-label="webhooks.playbooks.content">Content</span></strong>. Use <strong><span data-ui-label="webhooks.playbooks.preview">Preview</span></strong> or <strong><span data-ui-label="webhooks.playbooks.split">Split</span></strong> to inspect Markdown if needed.
3. Select <strong><span data-ui-label="webhooks.playbooks.createSubmit">Create playbook</span></strong> and confirm the new list entry.

Playbooks can be attached to both Sources and Rules and are added to event messages.

Example: “On a deployment failure event, summarize the impact. Do not guess unconfirmed causes; list the checks still needed.”

## Create an integration

1. In **Webhooks**, choose **New integration**, then **Set it up yourself**.
2. Review the service, name, and receiving organization, and configure signature verification, a secret, and rate limits as needed.
3. After creating the connection, register its receiving URL and required signing values with the external service.
4. Continue to automation creation from the result, or open **Automations** and create a webhook automation using this connection. Creating the connection and configuring event processing are separate steps.

Plaintext secrets may appear only during creation, regeneration, or rotation. Store them according to organization policy, never in documents or Chat.

## Choose targets with a webhook automation

1. Open **Automations → Create automation → Create manually → Webhook**. Continuing from a connection's creation result can preselect that connection.
2. Set the name, connection, event conditions, and recipients. Select one or more Agents or Rooms.
3. For multiple targets of the same type, choose a distribution method. Agents offer **Broadcast**, **Round Robin**, or **Idle First**; Rooms offer **Broadcast** or **Round Robin**.
4. Set a playbook describing the work and any required delivery limits, then save.
5. Check the new automation and its enabled state in the list. The connection's detail screen also links to its automations.

The Source and target Agents or Rooms must belong to the same tenant. Check access and select the intended targets. See [automation guidance](../capabilities/automation-and-webhooks.mdx) for schedules, message triggers, and status checks.

### Choose a distribution method

When you select multiple Agent targets, choose one of three options:

| Option | Behavior |
| --- | --- |
| Broadcast | Sends the event to all selected targets. |
| Round Robin | Distributes events across targets in turn. |
| Idle First | Prefers idle Agents. When all are busy, distributes events across eligible targets in turn. |

Room targets offer Broadcast and Round Robin.

If activity lookup fails with Idle First, routing can fall back to ordinary round-robin. This option does not queue events until a busy Agent finishes, so check event records and actual responses.

## Test and verify

Send a test event from the external service and check:

1. Receipt in <strong><span data-ui-label="nav.webhooks">Webhooks</span></strong> → <strong><span data-ui-label="webhooks.tabs.events">Events</span></strong>.
2. For an Agent target, delivery to that Agent's webhook Room and an executable Agent state.
3. For a Room target, a system message in the selected Room and the necessary participants.

The Agent receives the Source, Rule, event ID, JSON payload, and attached Playbook instructions as a message.

## Stop, rotate, and recover

Set the Source or Rule inactive to stop new events. For exposed secrets, rotate or regenerate the Source secret and immediately update the sender. Preserve Source, Rule, and Playbook configuration before potentially irreversible deletion.

No user-operated replay endpoint or automatic delivery retry has been verified for the current ingress. Inspect Event records, the target Room, and Agent status; recovery may require sending a new event from the external service.
